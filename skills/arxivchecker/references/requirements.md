# arXiv requirements and local-check boundaries

**Primary-source review date: 2026-11-03 (UTC).** This is an access date, not the effective date of every linked policy. Official arXiv pages were read directly. Toolchain snapshots and effective dates stated by those pages are identified below. Recheck current instructions and the submission UI before submitting.

This map separates official requirements, conditions, recommendations and optional local checks. It does not certify science, release rights, endorsement, authorship approval, moderation outcomes or arXiv acceptance. A limitation of a local tool must remain **unsupported or unassessed locally**, not become an arXiv rejection.

## Classification

| Classification | Meaning |
| --- | --- |
| Official requirement | A stated submission condition, prohibition or processing constraint. |
| Official format requirement (`should`) | The format-policy page calls these submission requirements, uses `should`/`should not`, and permits moderation to request corrections or individual changes. Preserve that nuance. |
| Conditional requirement | Applies only to the identified route, toolchain, feature or circumstance. |
| Official recommendation | Advice or preference; not a universal failure gate. |
| Local check or preference | A workflow/safety/portability choice or user preference; not arXiv eligibility. |
| Unverified/conflicting | Historical, ambiguous or inconsistent evidence; report uncertainty and confirm the applicable route. |

The last column describes assessment scope. TeX macros, package loading, search paths and generated inputs can defeat source regexes. A human checklist is not a completed machine verification.

## LaTeX source and typesetting recommendations

These improve readable, maintainable source and accessible HTML. They are recommendations or technical guidance, not additional universal arXiv acceptance gates. The [LaTeX Project documentation](https://www.latex-project.org/help/documentation/) explains authoring mechanisms; it does not set arXiv policy. Its current author guide covers newer features, while its explicitly historic guide remains linked for established LaTeX2e commands. Test against the TeX Live version selected for submission rather than assuming that the newest documented feature exists there.

| Practice | Scope and exceptions | Classification | Exact primary source | Local implementation/review |
| --- | --- | --- | --- | --- |
| Express document meaning through standard frontmatter, headings and emphasis commands. | Standard title/author/abstract markup, `\section` and `\emph` aid HTML structure; visual imitation alone may lose that meaning. No single document class or title-page arrangement is mandated by this advice. | Official arXiv recommendation for HTML/accessibility | [Structural markup](https://info.arxiv.org/help/submit_latex_best_practices.html#select-macros-that-describe-structures), [frontmatter](https://info.arxiv.org/help/submit_latex_best_practices.html#use-a-standardized-front-matter-block) | Review semantic source and converted headings/navigation where available. |
| Write useful image alternatives and preserve explanatory captions. | arXiv recommends the `graphicx` alt option. Check compatibility with the chosen package/toolchain; a missing alt option is not declared a universal rejection rule here. | Official arXiv recommendation | [Image alt text](https://info.arxiv.org/help/submit_latex_best_practices.html#alt-text-for-images) | Describe the visual's purpose and substantive information; inspect output rather than claiming PDF text extraction checks image accessibility. |
| Prefer packages supported by the HTML converter where practical. | Publisher-required packages may lack mappings; arXiv suggests seeking support. Unsupported HTML conversion does not alone establish that a TeX/PDF route is ineligible. | Official arXiv recommendation | [HTML package support](https://info.arxiv.org/help/submit_latex_best_practices.html#use-latex-packages-that-will-lead-to-good-html) | Check actual converter/toolchain behaviour and report partial conversion separately. |
| Use documented class/package controls and float/caption mechanisms. | Standard classes have paper, type, column and page-style options; these are mechanisms, not a mandatory journal style. Inspect title, tables, captions and float placement in the final document. | LaTeX technical guidance plus local editorial QA | [LaTeX author guide, §§2–3](https://www.latex-project.org/help/documentation/usrguide-historic.pdf), [standard classes, §§3,6–7](https://www.latex-project.org/help/documentation/classes.pdf) | Keep deliberate, consistent hierarchy and typography. Avoid brittle manual layout patches when class mechanisms suffice; no automatic failure for legitimate custom layout. |
| Use mathematical structures appropriate to the expression. | The AMS/LaTeX guide documents equation and alignment facilities; it does not require every article to use `amsmath` or one equation-numbering style. | Primary LaTeX/AMS technical guidance | [amsmath user guide](https://www.latex-project.org/help/documentation/amsldoc.pdf) | Preserve mathematical meaning, readable alignment and working references; inspect equations visually. |
| Teach clearly and use visuals to explain. | The owner's pedagogical voice, jargon treatment and explanatory-visual preferences are house style, independent of arXiv rules. | Local writing preference | [House writing guide](writing.md), [scholarly-presentation context](https://info.arxiv.org/help/moderation/index.html#scholarly-standards) | Apply the writing guide and judge whether a reader can follow the argument; never label house style an arXiv policy violation. |

## Conflicts and gaps that must not become false rejection rules

1. **Legacy versus current processing.** [Current TeX instructions](https://info.arxiv.org/help/submit_tex.html) describe Submission 1.5 and bibliography processing. [Legacy instructions](https://info.arxiv.org/help/submit_legacy_differences.html) describe an older no-BibTeX path. The [current processor list](https://info.arxiv.org/help/faq/texlive.html#supported-tex-processors) is more specific than stale unsupported-engine wording in the [mistakes FAQ](https://info.arxiv.org/help/faq/mistakes.html). Do not build an engine blacklist from that older passage.
2. **Figures.** The [overview](https://info.arxiv.org/help/submit/index.html#formats-for-figures) mentions GIF, whereas [PDFLaTeX-specific instructions](https://info.arxiv.org/help/submit_tex.html#considerations-for-pdflatex-submissions) use PDF/JPEG/PNG. The current [XeLaTeX guide](https://info.arxiv.org/help/faq/texlive.html#selecting-the-correct-processor) explicitly addresses mixed EPS/raster/PDF despite generic older mixing warnings. Apply current processor-specific guidance, convert/inspect uncertain assets or confirm with arXiv; do not impose one universal extension rule.
3. **Filename changes.** The overview gives a restricted set, while the FAQ describes automatic substitutions. Use safe original names/exact references; never assume upload renaming repairs dependencies.
4. **Size.** Historical 50 MB is not a current UI measurement. Current 34-megapixel warning measures pixel area, not archive bytes, and has PNG exceptions. Neither equals the helper's local cap. No undocumented total-byte or compression-accounting rule is inferred.
5. **Metadata encoding.** [Generic field advice](https://info.arxiv.org/help/prep.html#bad-characters) describes ASCII/TeX syntax, while the [accent subsection](https://info.arxiv.org/help/prep.html#note-on-latex-accent-commands) describes entered accented characters being converted. Follow current field syntax/UI; this is not a ban on Unicode TeX source or XeLaTeX.
6. **Policy wording and visual judgement.** Format-policy `should` conditions warrant review/correction, but regex hits alone do not prove rendered violations. Missing tools, unknown macros, optional comparison differences and pending visual review remain separate from established policy violations.
